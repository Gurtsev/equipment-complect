# Процесс выпуска изменений

Этот документ задаёт обязательный порядок поставки `equipment-complect`.

## 1. Подготовка

Перед коммитом:

1. Сверить изменение с `ROADMAP.md` и решениями в `docs/decisions/`.
2. Проверить влияние на frontend, Supabase, Nexus и 1С.
3. Для изменения архитектуры добавить или обновить ADR.
4. Для пользовательской функции обновить `CHANGELOG.md` и `docs/status.md`.
5. Не включать в тематический коммит посторонние изменения рабочей копии.

## 2. Локальная проверка

```powershell
npm.cmd run check
npm.cmd run build
git diff --check
```

`check` включает TypeScript typecheck и полный однократный прогон Vitest.

## 3. Изменения схемы БД

Каждое изменение схемы оформляется новой последовательной миграцией. Уже
применённые миграции не редактируются.

Безопасный порядок rolling deploy:

1. Аддитивная миграция, совместимая со старым frontend.
2. Новый frontend начинает использовать добавленную схему.
3. Удаление устаревших колонок — отдельной миграцией только после переходного
   релиза.

Если порядок временно обратный, frontend обязан:

- сохранять работу существующих функций со старой схемой;
- скрывать новую функцию до проверки готовности схемы;
- не отправлять новые колонки в старые операции.

Перед production-миграцией обязательны backup, проверочный SQL и инструкция в
`docs/deploy-*.md`.

## 4. Автоматическая поставка

Push в `master` запускает `.github/workflows/cd.yml`:

1. `quality`: `npm ci`, typecheck, тесты и проверка соответствия
   `supabase/combined_001_XXX.sql` последовательным миграциям.
2. `build-and-push`: Docker image с тегами `latest` и полным commit SHA.
3. `deploy`: production запускается именно на immutable SHA-теге.
4. `Verify production`: HTTP smoke-check `https://inventory.knzteam.ru/`.

Следующий job не запускается, если предыдущий завершился ошибкой. Одновременные
production-деплои выполняются последовательно.

## 5. Проверка после выпуска

После зелёного workflow:

1. Проверить изменённый пользовательский сценарий на production.
2. Проверить ошибки браузера и сетевые запросы.
3. Для Realtime открыть два независимых окна.
4. Для миграции выполнить post-check SQL из инструкции.
5. Перенести выпущенные пункты из `Unreleased` в версию/дату при подготовке
   именованного релиза.

## 6. Откат

Каждый image хранится под тегом commit SHA. Для отката на VDS нужно указать в
`~/inventory/docker-compose.yml` SHA последнего исправного коммита и выполнить:

```bash
docker compose pull
docker compose up -d --force-recreate
```

Откат frontend не откатывает БД. Перед необратимой миграцией должен существовать
отдельный проверенный план восстановления из backup.
