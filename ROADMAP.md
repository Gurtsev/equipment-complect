- **Обязательное условие для Этапа 5** — Edge Function-прокси (5.3) работает только на задеплоенном проекте

#### Решение проблемы сессии (persistSession + дедлок)
При деплое на GitHub Pages стандартный механизм сессий Supabase не работал: каждая перезагрузка требовала повторного входа.

**Причина 1 — `payload` error:** Supabase читает сохранённый JWT из localStorage, падает при декодировании → вызывает SIGNED_OUT.
**Решение:** `persistSession: false` — Supabase не управляет storage самостоятельно. Refresh token хранится в localStorage вручную (ключ `eq_rt_v1`). При перезагрузке вызывается `supabase.auth.refreshSession({ refresh_token })` — чистый обмен токена на сервере без локального декодирования JWT.

**Причина 2 — дедлок:** Supabase v2 держит внутренний мьютекс во время вызова `onAuthStateChange`. Вызов `supabase.from(...)` (fetchProfile) внутри колбека пытался захватить тот же мьютекс → вечный спиннер.
**Решение:** `onAuthStateChange` содержит только синхронные React state setters (`setUser`, `setLoading`). `fetchProfile` вынесен в отдельный `useEffect([user?.id])`, который выполняется после ре-рендера — вне скоупа мьютекса.

**Причина 3 — `getSession()` конфликт:** ручной вызов `supabase.auth.getSession()` при инициализации конфликтовал с внутренним `_initializePromise`, вешая все REST-запросы.
**Решение:** убран `getSession()`, состояние сессии получается исключительно через `onAuthStateChange`. Добавлен fallback-таймер 10 сек на случай отсутствия сессии.

### ✅ 4.2 Управление пользователями

**Модель доступа:** только почты вида `@megapolis.media` могут зарегистрироваться и войти. Остальные домены — отказ. Администратор может дополнительно добавить конкретные email из других доменов.

**Путь нового пользователя:**
1. Сотрудник открывает приложение → вкладка «Зарегистрироваться»
2. Вводит `@megapolis.media` email + придумывает пароль
3. Система проверяет домен через таблицу `allowed_emails` → создаёт профиль с ролью по умолчанию
4. Администратор при необходимости меняет роль в панели управления

**Реализация:**
- Таблица `allowed_emails`: `email` (конкретный адрес) или `domain` (например, `megapolis.media`) + `role`
- PostgreSQL триггер на `auth.users`: при регистрации проверяет `allowed_emails` по email и домену → создаёт запись в `profiles`
- Если email не в списке и домен не разрешён → профиль не создаётся → приложение показывает «Доступ запрещён»
- Вкладка «Зарегистрироваться» на странице входа (email + пароль)
- Страница администратора (только для роли `admin`): список пользователей, смена роли, деактивация, управление `allowed_emails`
- Восстановление пароля: «Забыли пароль?» на странице входа → письмо со ссылкой → форма нового пароля

### 4.12 Составные объекты учёта (ПК и комплекты)

**Задача:** поддержать иерархию «родитель — компоненты» для объектов, которые физически состоят из нескольких частей (ПК = системный блок + монитор + клавиатура и т.д.). С 1С сводится только родительская карточка — один ОС с одним инвентарным номером.

**Схема БД:**
- Миграция: колонка `parent_id uuid references equipment(id)` на таблице `equipment`
- Новый статус сборки: `assembly_status` (`assembling` / `ready` / `synced`) на родительской карточке

**Логика:**
- Компонент привязывается к родителю при создании или через редактирование карточки
- Родительская карточка показывает список компонентов и статус сборки
- **«Комплектуется»** → компоненты поступают постепенно; статус не меняется
- **«Готов к сверке»** → сотрудник склада сигнализирует, что комплект собран; карточка появляется в списке на сверку с 1С
- Инвентарный номер из 1С привязывается только к родителю
- Компоненты в 1С не сводятся — учитываются только в веб-сервисе
- При добавлении родителя в проект/займ — компоненты следуют автоматически

**UI:**
- `CreateEquipmentDrawer`: поле «Входит в состав» (Select из существующих карточек)
- `EquipmentDetail`: блок «Компоненты» для родителя; ссылка «Входит в состав: [название]» для дочерней карточки
- `CatalogSidebar`: дочерние карточки отображаются внутри родителя, не как отдельные строки списка (опционально)

**Интеграция с 1С (Этап 5):**
- Уведомление при поступлении каждого компонента: `type: "component"`, `parent_web_id`
- Сверка с 1С — только родительская карточка после перехода в статус «Готов к сверке»

### 4.11 Безопасность и целостность данных

По результатам аудита (май 2026). Приоритеты расставлены по уровню риска.

#### 🔴 Высокий приоритет

- **profiles RLS** (`005_history_user.sql`): политика `profiles_select using (true)` позволяет любому авторизованному пользователю читать email и роли всех сотрудников. Исправить: ограничить viewer только своим профилем, для истории — отдельная функция/view с только `id+name`
- **Триггеры целостности займов/выдачи**: создать loan/assignment можно на уже выданное оборудование — проверки только на клиенте. Добавить BEFORE INSERT триггеры на `equipment_loans` и `employee_assignments`
- **Валидация файлов при загрузке** (`CreateEquipmentDrawer`): нет проверки MIME-типа и размера файла. Добавить проверку на клиенте (image/*, max 10MB)
- **Race condition расходников** (`010_consumables.sql`): два одновременных списания могут нарушить остаток. Добавить `FOR UPDATE` блокировку в триггере

#### 🟡 Средний приоритет

- **`allowed_emails` видны всем**: viewer может прочитать список разрешённых доменов/email. Ограничить RLS только для admin
- **Тихие ошибки** (`EquipmentDetail`): `loadAssignment`, `loadLoan` молча глотают исключения — показывать пользователю сообщение об ошибке
- **Storage bucket**: любой оператор может загружать файлы. Добавить проверку роли в политику

#### 🟢 Низкий приоритет

- Audit log изменений на уровне БД (для compliance)
- Заменить `SELECT *` на явные поля в сервисах
- Валидация формата URL-параметра `?eq=`

## ⚡ Когда переходить к интеграции с 1С?

**Интеграция с 1С — это финальный этап, а не промежуточный.** Вот почему:

1С синхронизирует **инвентарные номера и МОЛ** (материально ответственное лицо). Чтобы это работало корректно, в веб-сервисе к тому моменту должно быть:

| Условие | Почему важно |
|---|---|
| Все единицы занесены в систему | Не с чем сверяться в 1С |
| QR-коды распечатаны и наклеены | Иначе «Склейка» (5.1) не имеет смысла |
| Карточки сотрудников работают (4.6) | МОЛ в 1С — это сотрудник; нужна та же модель в приложении |
| Схема данных заморожена | Изменения после синхронизации ломают маппинг |
| Команда реально пользуется сервисом | Интеграция с нерабочим инструментом бессмысленна |

**Рекомендуемый порядок:**
```
4.7 (✅) → 4.8 → 4.9 → [физическая оклейка QR] → Этап 5
```

Физическая оклейка — это организационный шаг вне кода, но именно она является точкой отсчёта для 1С: после неё каждая единица в системе имеет инвентарный номер и QR, и можно начинать «Склейку» (5.1).

## Этап 5 — Интеграция с 1С

Принцип: **Инвентарный номер — это мост**. 1С — источник юридической правды. Веб-сервис — мастер-система для техников.

### 5.1 Подготовка — «Склейка» существующих данных

- Выгрузка из 1С всех ОС с инвентарными номерами в Excel
- Выгрузка из веб-сервиса всех карточек оборудования
- Ручное сопоставление: ID карточки ↔ Инв. номер 1С
- Загрузка сопоставленных данных в веб-сервис (массовый UPDATE)
- Результат: все существующие карточки получают `sync_status = Synced`

### 5.2 Схема БД — поля синхронизации

Миграция: новые колонки в таблице `equipment`:
- `sync_status` — `'Draft' | 'Pending' | 'Synced' | 'Conflict'` (default `'Draft'`)
- `department` — подразделение из 1С
- МОЛ назначается в веб-сервисе (поле `responsible` уже существует на карточке)

### 5.3 Edge Function-прокси для 1С API + ограничение сессий

- Supabase Edge Function `one-c-proxy` — единственная точка обращения к 1С
- Хранит Basic Auth credentials в переменных окружения (не попадают к клиенту)
- Проксирует `GET /assets/free` и `POST /assets/sync` к 1С HTTP-сервису
- CORS-безопасно: вызов идёт сервер → сервер
- **Ограничение одновременных сессий:** не более 2 активных сессий на аккаунт. При входе с третьего устройства — автоматический отзыв самой старой сессии через `auth.admin.listUserSessions()` / `auth.admin.deleteUserSession()`. Требует `service_role` ключа → реализуется в этой же Edge Function

### 5.4 Сервис синхронизации `onecService.ts`

- `getFreeAssets()` — список свободных инвентарных номеров из 1С
- `syncAsset(inv_no, serial_no)` — привязать серийник к номеру 1С, получить МОЛ и подразделение
- Статусная машина: Draft → Pending → Synced / Conflict

### 5.5 UI — форма создания оборудования

- Поле `inv_number`: заменить текстовый ввод на динамический Select с поиском по 1С
- Поле `serial_number`: сделать обязательным
- Бейдж `sync_status` на карточке оборудования и в списке каталога
- Показывать МОЛ и подразделение в карточке (если Synced)

### 5.6 Фоновая синхронизация (Cron)

- Supabase `pg_cron` — SQL-функция каждые 30 минут
- Опрашивает все карточки со статусом `Pending`
- Проверяет статус списания (`active` / `written_off`) для карточек со статусом `Synced`
- При списании в 1С — автоматически обновляет статус оборудования на «Списано»

### 5.7 QR-коды и маркировка

- ✅ Библиотека `qrcode.react` — QR с URL на карточку: `?eq=EQP-####`, при открытии карточка открывается автоматически
- ✅ Печать: только QR + модель + инвентарный номер (остальное скрыто)
