# Changelog

Значимые пользовательские изменения проекта фиксируются в этом файле.

## Unreleased

### Added

- Импорт переиспользуемого списка оборудования в проект с предварительным
  сравнением доступных, существующих и недоступных позиций.
- История импорта списка в проект с количеством добавленных и пропущенных позиций.
- Автоматические тесты анализа состава импортируемого списка.
- Идемпотентная миграция, синхронизирующая Supabase Realtime publication с
  таблицами, которые слушает frontend.
- Проверка типа и размера изображения оборудования до загрузки.
- Migration-first RPC для атомарного создания карточки оборудования вместе с
  первой записью истории (миграция 031).
- Migration-first RPC для атомарной смены статуса сборки
  составного объекта и записи его истории (миграция 032).

### Changed

- После production-применения миграций 029–030 frontend больше не выполняет
  неатомарные legacy-запросы при отсутствии RPC: операция завершается
  ошибкой без частичных изменений данных.
- После production-применения миграции 031 карточка оборудования и её первая
  запись истории создаются одним атомарным RPC.
- После production-применения миграции 032 статус сборки и его запись
  истории изменяются одним атомарным RPC.
- Расширенная история проектов из миграции 024 теперь также обязательна:
  импорт списка не скрывается, а ошибка схемы не маскируется legacy-чтением.
- Карточка проекта показывает ошибку загрузки истории вместо пустого списка и
  не открывает добавление оборудования, если не удалось проверить активные займы.
- Создание, редактирование, наполнение, активация и завершение проекта вместе с составом, займами и историей выполняются транзакционными PostgreSQL RPC; конфликты оборудования проверяются на сервере после миграции 030.
- Выдачи, займы и возвраты выполняются через транзакционные PostgreSQL RPC: custody-запись и история оборудования теперь изменяются атомарно после применения миграции 029.
- Frontend-запросы к Supabase используют явные наборы полей вместо wildcard-проекций.
- Deep links `?eq=` и `?room=` валидируются и больше не удаляют посторонние query-параметры; при двух целях выбирается оборудование.
- Крупные экраны и drawer-компоненты загружаются по требованию; стартовый JS уменьшен примерно с 612 до 260 КБ gzip и защищён build-бюджетом 300 КБ.
- Supabase атомарно запрещает повторную выдачу занятого оборудования, одновременную выдачу и займ, пересекающиеся займы и некорректный период займа.
- Карточка оборудования показывает ошибки загрузки и понятную причину отказа при конфликте выдачи или займа.
- Операции с расходниками теперь блокируют остаток на время изменения и целиком отклоняются при недостаточном количестве вместо частичного списания.
- Списки оборудования стали независимыми шаблонами; проект хранит собственный
  фактический комплект и после импорта редактируется отдельно.
- Frontend сохраняет чтение и запись обычной истории проектов при rolling deploy,
  пока миграция списков ещё не применена; импорт до этого момента скрыт.
- Открытая карточка оборудования сразу показывает новый статус после сохранения;
  помещения и история открытого проекта обновляются через Realtime.
- Viewer больше не может изменять Storage, а allowlist email/доменов доступен
  только администратору.
